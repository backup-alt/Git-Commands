Git • Quick Reference

Push your latest code.

A clean cheat sheet for the Git commands you actually need — from your first push to everyday updates.

Everyday workflow

Use this when the repository is already connected to GitHub.

git status -sb
git add <files>
git commit -m "Your message"
Can't think of a commit name?

Generate a random commit message and copy it.

git pull --rebase origin main
git push
git status -sb
Think: Check → Stage → Commit → Sync → Push → Confirm

First push to a new GitHub repo

Use this when you have a local project and a completely empty GitHub repository.

cd path\to\your-project
git init
git add .
git commit -m "Initial commit"
git branch -M main
git remote add origin https://github.com/USERNAME/REPO.git
Customize the repository URL

Paste your GitHub repository URL and the command will be generated automatically.

git push -u origin main
After this: Git remembers the upstream, so future pushes can simply use git push.
Important: If the GitHub repo already contains a README, .gitignore, license, or other commits, don't blindly use this workflow. The histories need to be reconciled first.

When Git says you can't push or rebase

This is the safe recovery flow for the exact situation where you changed a file, forgot to stage it, and GitHub has commits you don't have locally.

Don't panic — your changes are still there.
If Git says Changes not staged for commit, it means your file was changed but has not been added to the next commit yet.

Step 1 — Check what actually changed

git status -sb

Look at the exact filename Git shows. In your case it was git.html, not index.html.

Step 2 — Stage the file you actually changed

git add git.html

Replace git.html with the filename shown by git status.

Step 3 — Commit your change

git commit -m "Update Git command guide"

Step 4 — Bring GitHub's changes into your branch

git pull --rebase origin main

Step 5 — Push

git push -u origin main
Why this works: You first save your local HTML change in a commit. Then Git can safely rebase that commit on top of the commits already on GitHub. Finally, you push the combined history.

If you haven't committed yet

If git pull --rebase says You have unstaged changes, do this instead:

git status -sb
git add <the-file-Git-showed>
git commit -m "Your message"
git pull --rebase origin main
git push

If you really don't want to commit your changes yet

Temporarily put your local changes aside, update from GitHub, then bring your changes back.

git stash push -m "WIP"
git pull --rebase origin main
git stash pop
Don't use this just to fix a normal push. If your change is ready, committing it first is usually simpler.

If you accidentally stage the wrong file

git restore --staged <file>

This removes the file from staging but does not delete your actual changes.

Never use git reset --hard as a random fix. It can permanently discard local work. Only use destructive Git commands when you know exactly what they will remove.

Your exact situation

For the commands you just ran, this is what happened.

1. Commit failed

You changed git.html, but did not stage it first.

git add git.html

2. Wrong filename

You ran git add index.html, but that file doesn't exist in this project.

3. Push was rejected

GitHub already has commits that your local branch doesn't have.

git pull --rebase origin main

4. Rebase was blocked

Your git.html change was still unstaged, so Git refused to start the rebase.

The fix from your current state:
git add git.html
git commit -m "Update Git guide"
git pull --rebase origin main
git push -u origin main

GitHub Pages — rebuild & deploy

Use the workflow that matches how your frontend is deployed. For modern frontend projects, GitHub Actions is usually the cleanest option.

First check your project: Run git status -sb and make sure your changes are committed before rebuilding or deploying.

A. Build the frontend locally

For Vite / React / most Node-based frontend projects:

npm install
npm run build

This normally creates a dist folder. Some projects use build instead.

B. Test the production build locally

If your project provides a preview script:

npm run preview

C. Commit and push your source changes

git status -sb
git add <files>
git commit -m "Update frontend"
git pull --rebase origin main
git push origin main
With GitHub Actions: If your repository is configured to deploy automatically on pushes to main, the push above is enough. GitHub Actions will install dependencies, build the frontend, and deploy it.

D. Manually trigger the GitHub Action

If the workflow has workflow_dispatch enabled, go to GitHub → Actions → select your frontend deployment workflow → Run workflow.

E. Check the deployment from the terminal

See the latest workflow runs:

gh run list

Watch the latest run:

gh run watch

These require the GitHub CLI (gh) to be installed and authenticated.

F. If the Action failed

Get the failed workflow logs:

gh run view --log-failed

Fix the frontend/build issue, then commit and push again:

git add <files>
git commit -m "Fix deployment"
git pull --rebase origin main
git push origin main
Important: Don't automatically commit the generated dist folder. With a GitHub Actions deployment, the workflow should normally build dist and publish it for you. Follow your repository's existing deployment configuration.

Quick deployment routine

If your GitHub Action is already configured to deploy on every push to main:

npm run build
git status -sb
git add <files>
git commit -m "Update frontend"
git pull --rebase origin main
git push origin main
Then: GitHub → Actions → watch the deployment → open your GitHub Pages site.

Useful commands

Check remote changes

Downloads remote commits without changing your files.

git fetch origin

See remote commits

Shows the latest six commits on GitHub's main branch.

git log --oneline origin/main -6

Pull without rebase

Fetches and merges remote changes.

git pull origin main

Push a new branch

First push for a newly created branch.

git push -u origin my-feature-branch

Rebase conflict

After resolving a conflict in the files.

git add <resolved-file>
git rebase --continue

Cancel rebase

Returns you to the state before the rebase started.

git rebase --abort

When push is rejected

Usually means the remote branch has commits you don't have locally.

git pull --rebase origin main
git push
